description: Choose a proportionate workflow for business analysis, requirements, architecture and delivery. Use for substantial multi-step work, evidence, selective diagramming and project lessons. Skip simple factual or wording tasks.
---

Use the recipient's language, preferences, account and project tracker. This is a generic portable core, not the owner's private full backup and not an autonomous worker. Read only the selected template or diagram entry.

1. Establish the task, current versions, constraints, acceptance criteria and permitted data destinations. Inspect existing project sources before asking for known context. For business analysis select `templates/analysis.md`; keep requirements, decisions and tests traceable.
2. For an unknown solution, find verifiable analogues in primary docs/public repositories. Compare architecture, versions and constraints before adapting the smallest adequate solution. Check source/pin, license, relevant code/dependencies/install scripts, network and secret access. Do not run unchecked installers. Known simple work does not require a research ritual; checks are proportionate and never prove absolute safety.
3. Use diagrams only on explicit request or when they resolve an actual decision. Use `references/diagrams/index.json` to select a family and read one model. Preserve notation semantics, scope, assumptions, current/target status and editable source. Original SVG/draw.io/BPMN exports work offline; native engine examples are optional and were not executed here. Never send private project data to public renderers without authorization. Exact engine licenses/versions must be checked before installation; no upstream code is bundled.
4. Implement or document the agreed result; verify in isolation and retain rollback for meaningful changes. Existing user/host authorization governs external writes and agent delegation. Do not create paid resources, broaden access, contact others or schedule background work on the strength of this skill.
5. Before work, search only relevant accepted project lessons by project/topic. After a meaningful stage, fill `templates/lesson.json` with confirmed action, failed hypothesis if any, evidence and applicability. Keep private records in the recipient's project; update a compact project/topic index of pointers. Promote a general rule only with sufficient reviewed evidence. Do not ingest all archives or projects automatically. Time estimate, execution, permission wait, tool wait and access wait remain separate; unknown values are null, never guessed.
6. Keep the cloud plugin, independent private source backups, host cache and project data distinct. Store versioned full ZIP, licenses, hashes, manifest, external receipt and LATEST in approved GitHub/Drive destinations; verify download/readback and owner-only access. A CI configuration does not prove current execution or automatic cloud/Drive sync. Read `templates/recovery.md` for loss of a computer or transfer to another person. Never publish private backup history or personal logs to make a package shareable.

Report what passed, what was not tested and the exact blocker. File presence, source publication, successful unit tests and fresh-session skill discovery are separate claims. No credentials or other person's private context belong in this package.
